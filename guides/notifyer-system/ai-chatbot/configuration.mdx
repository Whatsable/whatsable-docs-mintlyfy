<Tip>
You can create as many agents as your plan allows and assign them per WhatsApp number. The configuration form is the same whether you are creating a new agent or editing an existing one.
</Tip>

## Opening the form

- **Create**: From the [AI Chatbots](/guides/notifyer-system/ai-chatbot/overview) dashboard, click **Create agent**.
- **Edit**: Click **Edit** on any existing agent. The form loads with saved values pre-filled.

The editor sidebar follows this order:

1. **Agent identity**
2. **Knowledge base**
3. **Files it can send**
4. **Custom instructions**
5. **Response settings**
6. **Labels**
7. **Notifications**
8. **Follow-ups**
9. **Review** (readiness checklist — not a separate saved field)

New agents start as **Draft**. Activate or archive them from the dashboard list, not from this form body.

---

## Agent identity

Defines who the agent is for your team. Customers never see these fields.

<ResponseField name="Name" type="string" required>
  An internal label operators see in the inbox and on the assign menu (for example `Sales concierge`). Max **60** characters.

  Customers never see this name.
</ResponseField>

<ResponseField name="Mission" type="string" required>
  One sentence the agent works from on every reply — what the job is (pricing, booking, qualifying leads). Max **20,000** characters.

  Rules and exceptions belong in **Custom instructions**, not here.

  **Good example:** `Qualify inbound leads, answer pricing questions from our published tiers, and book a demo when the customer is ready.`
</ResponseField>

<Info>
“Default” is **per WhatsApp number**, not a single flag on the agent itself. An agent becomes the org-wide default when every connected number points at it (dashboard **Set as default** / number assignment).
</Info>

## Knowledge base

Price lists, policies, and product sheets the agent answers from. Knowledge is **optional for Save** — an agent can still be saved with only Name, Mission, and Instructions — but without knowledge it answers only from the mission and custom instructions.

### Data sources (file uploads)

<ResponseField name="Add data source" type="file[]">
  Upload documents Whatsable parses into text for the agent. Supported formats:

  | Format | Notes |
  |--------|-------|
  | `.pdf` | Text is extracted; image-only PDFs yield no content |
  | `.txt` | Plain text, read as-is |
  | `.md` | Markdown |
  | `.csv` | Useful for catalogues or FAQ tables |
  | `.docx` | Word documents; text extracted automatically |

  **Limits:** each file must be within the media size cap (typically **10 MB**). On create, files stay **staged** until the first successful save, then upload.

  Statuses you may see: **Processing**, **Ready**, **Failed**, or **Waiting** (staged). Failed reasons are closed classes such as unsupported type, timeout, unreadable, or empty — never a raw parser dump.
</ResponseField>

<Warning>
If the agent is **Archived**, knowledge uploads are disabled until you restore it.
</Warning>

### Written knowledge

<ResponseField name="Anything the files do not cover?" type="string">
  Short facts that belong in text rather than a file: hours, a delivery price, a promise you never make. Max **200,000** characters.

  Leave this empty if uploads cover everything. Empty knowledge does **not** block Save (it only affects the readiness score).
</ResponseField>

## Files the agent can send

Distinct from the knowledge base. **Knowledge is what the agent knows. Files are what it can send** — the agent never reads the file bytes; it chooses a file only from the description you write.

Cap: **10** sendable files per agent.

<ResponseField name="What the file you are adding is for" type="string" required>
  Required to add a file. Max **1,000** characters. This sentence is the only thing the model uses to decide when to send the attachment.

  **Example:** `The 2026 price list, with delivery times for each region — send when a customer asks for pricing in writing.`
</ResponseField>

<Warning>
A sendable file **without a description** cannot be chosen by the agent. Write a clear description before you rely on the agent to send that file.
</Warning>

<ResponseField name="What to call the file you are adding" type="string">
  Optional display name (max **120** characters). Falls back to the original filename when empty. Editable later without re-uploading.
</ResponseField>

<ResponseField name="The agent may send this file" type="boolean" default="true">
  Per-file switch. Turn off to keep the file uploaded but stop the agent from sending it, without deleting the row.
</ResponseField>

<Warning>
Archived agents cannot accept new sendable files until restored. On create, chosen files stay staged until the first save.
</Warning>

## Custom instructions

<ResponseField name="Instructions" type="string" required>
  Rules for every reply this agent sends. The mission says what the job is; these lines say how to do it. **Required to Save** in the current editor. Max **80,000** characters.

  Write **one rule per line**. Typical uses:

  - Topics the agent must never discuss
  - Questions it must ask before booking or quoting
  - Formatting preferences
  - When to add or remove a label (name the label exactly as it appears under **Labels**)

  **Example:**

  ```
  Always ask for the customer's order number before discussing a refund.
  Never mention competitor products.
  If you do not know, say so — do not invent a price.
  Add Hot lead when they ask to reserve or hold stock.
  ```
</ResponseField>

## Response settings

Controls how the agent communicates and when it returns after a human reply — not what facts it knows.

### How should the agent sound?

<ResponseField name="Tone" type="string">
  Free-text voice for ordinary replies (max **300** characters). Blank is allowed; when blank at runtime the platform falls back to a friendly default.

  Four presets fill the input (you can still edit the text afterward):

  | Preset | Feel |
  |--------|------|
  | **Friendly** | Warm, informal |
  | **Professional** | Clipped, precise |
  | **Balanced** | Middle ground |
  | **Enthusiastic** | High energy |

  Follow-up voice is steered separately under **Follow-ups** → **What to say in a follow-up**.
</ResponseField>

### How long should the agent wait before it sends a reply?

<ResponseField name="How long should the agent wait before it sends a reply?" type="integer (seconds)" default="5">
  Debounce after the customer writes, before the agent’s answer goes out. Range **0–300** seconds (slider). Default **5**.

  **0 is legal** — the turn can start immediately. A short wait feels more human and lets several quick messages batch into one reply.

  This wait **does not** apply to proactive follow-ups.
</ResponseField>

<Tip>
**Recommended starting point:** about 8–12 seconds for most businesses. Use a low value for high-volume queues; raise it when customers tend to send several short messages before finishing their question.
</Tip>

### Once you reply by hand

<ResponseField name="Once you reply by hand" type="enum" default="never">
  What happens after you or a teammate reply manually (including from the WhatsApp Business app). Options:

  | Option | Behaviour |
  |--------|-----------|
  | **The agent stays off until someone turns it back on** (`never`) | Default. Agent stays quiet on that chat until re-enabled. |
  | **The agent resumes when the customer starts a new conversation** (`new_session`) | Stays off for the current session; returns on a new conversation. |
  | **The agent resumes after a set time** (`timer`) | Stays quiet for the duration you set, then can answer again. |
</ResponseField>

<ResponseField name="Resume after (minutes)" type="integer (minutes)">
  Shown only when the policy is **The agent resumes after a set time**. Range **1–10,080** minutes (1 minute to 7 days). Required when that policy is selected.

  The quiet period restarts if you write again. Replies from the Whatsable dashboard vs the mobile app may differ in how the timer is started — see [Shared team inbox](/guides/notifyer-system/team-inbox) for operator behaviour in the live chat.
</ResponseField>

## Labels

Lets the agent add or remove conversation labels you grant it. Powers default **on**.

<ResponseField name="Let this agent add labels" type="boolean" default="true">
  When on, the agent may tag conversations according to your label instructions and grants.
</ResponseField>

<ResponseField name="Let this agent remove labels" type="boolean" default="true">
  When on, the agent may remove granted labels when instructions say so.
</ResponseField>

<ResponseField name="Most labels to add in one reply" type="integer | null">
  Shown when add is enabled. Range **1–5**. Leave unset (**Use the maximum**) to use the platform max of **5**.
</ResponseField>

<ResponseField name="Most labels to remove in one reply" type="integer | null">
  Same pattern as the add cap: **1–5**, or unset for the platform max of **5**.
</ResponseField>

<ResponseField name="Which labels this agent may use" type="enum" default="all">
  | Mode | Behaviour |
  |------|-----------|
  | **Every label** (`all`) | May use any label in the organization, including ones created later. Grant checkboxes appear selected and disabled. |
  | **Only the ones I pick** (`listed`) | May use only the labels you tick (max **20**). |
</ResponseField>

<Warning>
If label powers are **on**, grant mode is **Only the ones I pick**, and **no labels are ticked**, the agent has nothing it can apply. The editor shows a readiness warning — labels will look broken until you grant at least one label or switch to **Every label**.
</Warning>

<ResponseField name="When to apply a label" type="string">
  Policy text the model reads every turn (max **10,000** characters). Describe the moment in plain language.

  **Example:** `Add Hot lead when they ask to hold stock. Remove it once they pay.`
</ResponseField>

## Notifications

When a customer wants a person, the agent steps back, the thread can be left unassigned, and a teammate can pick it up. Keywords catch explicit phrases; the situations box catches the rest.

There is **no** separate notification toggle on this form (including no “Human Agent Request Notification” control). Configure keywords and situations here; team alerting follows product handoff behaviour.

### Which words mean they want a person?

<ResponseField name="Which words mean they want a person?" type="string[]">
  Words or short phrases that, when present in a customer message, signal human assistance. Matching is **case-insensitive**.

  Limits: up to **25** keywords, each up to **120** characters.

  **Common examples:** `agent`, `human`, `speak to someone`, `real person`, `talk to a person`

  Add rows with **Add keyword**; remove with the control on each chip.
</ResponseField>

### Besides those words, when should it hand over?

<ResponseField name="Describe those situations" type="string">
  Plain-language situational escalation — anger, a large refund, a safety issue — even when no keyword matched. Max **10,000** characters. This is **policy for the model**, not a WhatsApp message body.

  **Example:** `Hand over when the customer is frustrated or angry; when discussing refunds over $500; when a product safety issue is reported; when three exchanges have not resolved the issue.`

  Leave blank if you only want keyword-based handoff.
</ResponseField>

<Info>
Keywords and situations work together. Keywords catch explicit asks; situations catch contextual ones.
</Info>

## Follow-ups

Outbound chase when a conversation goes quiet after your side (or the agent) sent a WhatsApp message. Cadence fields appear only while follow-ups are enabled; turning the master switch off hides them in the UI but stored values are kept for when you turn it back on.

### Master switch

<ResponseField name="Follow up when a conversation goes quiet" type="boolean" default="false">
  Master switch. Off by default. When on, an unanswered outbound message can start a follow-up sequence inside the budget and window you set.
</ResponseField>

### Cadence

Enter delays as **days + hours + minutes** (they add up to a single minute total stored by the API).

<ResponseField name="Wait before the first follow-up" type="integer (minutes)" default="240">
  Delay from the unanswered outbound before the first follow-up. Range **1–43,200** minutes (**30 days**). Default **4 hours**. Must be **strictly less than** **Stop following up after**.
</ResponseField>

<ResponseField name="Stop following up after" type="integer (minutes)" default="7200">
  Hard stop window from that same unanswered outbound. Range **2–129,600** minutes (**90 days**). Default **120 hours** (5 days).

  Every follow-up in the stretch must go out before this deadline.
</ResponseField>

<Note>
Some on-screen validation copy may still mention a **30-day** window maximum. The platform contract allows up to **90 days**.
</Note>

<ResponseField name="How many follow-ups at most" type="integer" default="3">
  Budget for **one quiet stretch**, not a lifetime cap. Range **1–15**. Default **3**. If the customer replies and later goes quiet again, the budget can restart for the new stretch.
</ResponseField>

<ResponseField name="Minimum gap between follow-ups" type="integer (minutes)" default="0">
  Minimum spacing between one follow-up and the next. Range **0–43,200** minutes. Default **0**.
</ResponseField>

<ResponseField name="How to space them" type="enum" default="front_loaded">
  | Option | Behaviour |
  |--------|-----------|
  | **Evenly** | Same gap between each follow-up |
  | **Sooner rather than later** | More of them early in the window (default) |
  | **Later rather than sooner** | More of them toward the deadline |

  A slot that would land in quiet hours or on a quiet day is **skipped**, not moved to the next open slot.
</ResponseField>

### Quiet hours, quiet days, and timezone

<ResponseField name="Do not send between" type="integer pair (0–23) | empty">
  Quiet-hour start and end (hours **0–23**). Leave **both** empty to allow any hour. Setting only one side clears both on save.
</ResponseField>

<ResponseField name="Do not send on" type="day toggles">
  Whole calendar days with no follow-ups (Sunday–Saturday), evaluated in the follow-up timezone.
</ResponseField>

<Warning>
You cannot mark **all seven** weekdays as quiet. That would make every follow-up impossible; leave at least one day open, or turn follow-ups off.
</Warning>

<ResponseField name="Times are local to" type="IANA timezone" default="UTC">
  Timezone for quiet hours and quiet days (for example `Europe/Madrid`). Curated list plus stored or browser zones. Default **UTC**.
</ResponseField>

### Follow-up content and risky toggles

<ResponseField name="What to say in a follow-up" type="string">
  Used **only** when composing a follow-up, not ordinary replies. Max **12,000** characters. Say what to offer, what never to promise, and not to repeat the last message.
</ResponseField>

<ResponseField name="Keep following up even after a reply from your side" type="boolean" default="true">
  **On by default.** The agent can still follow up when a customer goes quiet after your side replied — from the inbox, the WhatsApp phone app, or your own API integration.
</ResponseField>

<Warning>
**Keep following up even after a reply from your side** defaults to **on**. That is easy to miss: follow-ups can continue after a human, phone-app, or API outbound. Turn **off** so any outbound from your side ends follow-ups on that conversation for good.
</Warning>

<ResponseField name="Also follow up after a broadcast" type="boolean" default="false">
  **Off by default.**
</ResponseField>

<Warning>
Turning **Also follow up after a broadcast** on can start a follow-up sequence for every recipient of a large blast. Keep it off unless you intentionally want that blast radius.
</Warning>

<ResponseField name="Let the agent write templates" type="boolean" default="false">
  **Off by default.** Outside the customer **24-hour** service window, WhatsApp only allows an approved template. With this on, the agent may propose a new template for Meta review on your WhatsApp account — enabling it is that consent. Templates it wrote are marked in your template list.
</ResponseField>

<Warning>
A follow-up sent **outside the 24-hour window** is treated as **marketing**. It is subject to per-country limits and can affect your number’s quality rating. Enable **Let the agent write templates** only if you understand that trade-off; turning authoring on is Meta template-submit consent.
</Warning>

<ResponseField name="Templates it may propose per week" type="integer" default="2">
  Shown only when template authoring is on. Range **0–20**. Default **2**.
</ResponseField>

## Saving the configuration

Click **Save** when ready. The editor blocks save until:

1. **Name** is not empty  
2. **Mission** is not empty  
3. **Instructions** are not empty  

Knowledge text and knowledge files are **not** save blockers (they affect readiness score only). Follow-up cadence fields are validated when follow-ups are enabled (ranges, first delay inside the window, quiet-day rules).

On success the agent is created or updated and you return to the AI agents list. New agents are not automatically the default — assign numbers or use **Set as default** on the dashboard.

<Note>
Editing an agent does **not** rewrite conversations already in progress. Changes apply to the **next** message processed after save.
</Note>

### Related tools (not config fields)

- **Improve my agent** — helps organize mission, knowledge, instructions, handoff, and follow-up text before you apply them to the form.
- **Test your agent** — sandbox preview; nothing is sent to WhatsApp.
- **Review** — live readiness checklist before save.
